BUG 1 — background showed the PREVIOUS skin until a full restart
--------------------------------------------------------------------------
YOUR HYPOTHESIS WAS THE CACHE. IT WASN'T. Reporting the real cause.

The texture cache is innocent. SurfaceTexture._cache is keyed by texture id,
and those ids are already unique per skin ('night_ops', 'woodland',
'dress_blues_twill', 'dress_blues_metal'). No two skins can collide, so no
invalidation was ever needed and adding the skin id to the key would have
fixed nothing.

ROOT CAUSE — the widget never rebuilt.
  app.dart mounted the layer as:
      const Positioned.fill(child: GlobalSkinBackground())
  and GlobalSkinBackground was a const StatelessWidget reading the mutable
  static FieldManual.skin.

  Const widget instances are canonicalized by the compiler, so every rebuild
  of the router builder passed the IDENTICAL instance. Element.updateChild
  short-circuits on identical(newWidget, oldWidget) and skips the rebuild
  entirely. build() therefore ran exactly ONCE, captured whichever skin was
  equipped at first frame, and constructed a painter around it forever.
  shouldRepaint returns false, so nothing ever refreshed it either.

  Equipping a new skin updated FieldManual.skin and every Riverpod-driven
  colour — which is why accents/trim changed correctly — while the texture
  layer kept painting the old skin. Only a process restart rebuilt it.

PROOF (not inference): test/unit/global_background_skin_switch_test.dart.
  Written BEFORE the fix, it failed on the FIRST assertion — the widget
  painted nothing at all for a theme supplied purely via the provider,
  because it never consulted the provider.

FIX
  GlobalSkinBackground is now a ConsumerWidget that watches
  activeThemeProvider and derives texture/header/bandHeight from the WATCHED
  theme rather than the static. The call site is no longer const.

  * A skin switch rebuilds it live — the test drives a real provider change
    (no re-pump, no restart) through night_ops -> woodland -> dress_blues ->
    Field Manual and asserts the painted texture id follows each time.
  * Ordinary navigation still does NOT rebuild it: it sits above the
    navigator and depends only on the theme, so routes come and go beneath
    it. Still wrapped in RepaintBoundary, still mounted once, no flash.
  * Deriving from the watched value also removes the ordering dependency on
    app.dart having written the static first.

BUG 2 — AUDIT: texture missing on dashboard/nutrition/progress, present on settings
--------------------------------------------------------------------------
REAL CAUSE, and it is NOT what the scaffold-token scoping covered.

The first sweep converted `backgroundColor: palette.background` ->
`palette.scaffold`. It did nothing for screens that hardcode the OTHER ground
token, `FieldManual.ink`. Those screens kept painting an opaque fill — and
because FieldManual.ink is skin-driven it returned the Dress Blues navy, so
the pages looked like a flat navy skin rather than an obviously broken one.

23 screens were affected. That maps exactly onto what you saw.

DASHBOARD SPECIAL CASE — confirmed clean.
  dashboard_screen.dart:301 still reads `body: SkinBackground(child: body)`,
  but SkinBackground is now a PASS-THROUGH for texture skins (returns `child`
  unchanged; only non-texture themes still get its ColoredBox). It builds no
  painter, so there is no double-handling and nothing fighting the global
  layer. Dashboard's only problem was its own opaque scaffold at :262.

FIX APPLIED
  New static FieldManual.scaffold, the twin of Palette.scaffold:
      skin.surfaceTexture == null ? skin.ink : transparent
  It exists because most of these screens set a scaffold colour with no
  Palette in scope. All 23 `backgroundColor: FieldManual.ink` sites were
  converted to it.

  DELIBERATELY NOT CONVERTED — 18 `color: FieldManual.ink` sites. Those are
  modal sheets, action sheets and card fills (add-food, quick-add, paywall
  sheet, emoji picker, theme preview, …). A sheet is a surface, not a ground;
  making it transparent would drop dense content straight onto the texture
  and wreck readability. Nav bars likewise keep their opaque backdrop
  (FieldManual.ink.withValues(alpha: 0.82)), per your instruction.
